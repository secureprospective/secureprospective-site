# NARRATIVE — 2026-08-27, cycle24. Demo is 09:30 CST today.

## The headline: DN-15's real cause is found, and it was never the theme.

Three cycles were spent on the plymouth theme and the script plugin. Both were
necessary, both are correct now, and NEITHER WAS THE CAUSE. The cycle24 panel
strip settled it: frames f11-f22 -- twenty-four seconds while the LUKS
passphrase was being asked -- show GRUB's plain "Booting a command list" text
on a VGA console. Plymouth had not taken the panel at all. We were fixing what
plymouth would draw while plymouth was never getting the screen.

The installed kernel command line carries no rhgb:
  ... ostree=/ostree/boot.1/default/<sha>/0 console=ttyS0,115200

Fix committed (5786fd6) as /usr/lib/bootc/kargs.d/10-sp-plus-splash.toml with
kargs = ["rhgb", "quiet"], so the image owns it and it survives bootc upgrade.
bootc container lint validates that directory and passes.

## The caveat that matters more than the fix

The lane's own spb-boot appends console=ttyS0,115200, which independently sends
everything to the serial and leaves the panel dark. So the black screen is at
least partly MY INSTRUMENT, not the product.

Re-booting cycle24's disk with " rhgb quiet console=tty0" injected at the GRUB
editor made the prompt appear on the panel -- screen-luks.png went from 1611
bytes (blank) to 5913 bytes showing:
  Started plymouth-start.service - Show Plymouth Boot Screen.
  Please enter passphrase for disk QEMU_HARDDISK (luks-73d86a46-...)::_
It appeared as TEXT, not as the graphical SP+ splash.

CONTROL RUN READ -- THE QUESTION IS SETTLED. Booting with " console=tty0"
ALONE, no rhgb, screen-luks.png came back 11225 bytes showing:
  Please enter passphrase for disk QEMU_HARDDISK (luks-73d86a46-...)::_

So console=tty0 was the whole cause. THE BLACK SCREEN WAS THE LANE, NOT THE
PRODUCT. DN-15 as originally written -- "the machine looks dead at the
passphrase prompt" -- is NOT a hardware defect, and three cycles of plymouth
theme work chased an artifact of spb-boot's own console=ttyS0,115200.

rhgb quiet is still worth shipping, but for the honest reason: without it the
advisor sees a wall of scrolling systemd text (visible in that control frame);
with it they should see the branded splash. That is POLISH, NOT RESCUE. Do not
let anyone re-open this as a boot-blocker.

Note for whoever picks this up: the demo machine has no console= argument at
all, so tty0 is its console by default. That means the Dell probably never had
the black screen we were chasing -- it would have shown text messages and a
text prompt. The remaining real question is whether the GRAPHICAL SP+ splash
renders, and the VM cannot answer it: plymouth fell back to text there, most
likely because of the virtual GPU. That question can only be closed on the
hardware.
