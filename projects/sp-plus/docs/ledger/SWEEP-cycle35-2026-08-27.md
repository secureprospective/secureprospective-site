# SP+ cycle35 — full system sweep

Run 2026-08-27 ~19:00 CDT over SSH into the installed guest `fedora-test35`
(port-forward `127.0.0.1:2235` hot-added via the QEMU monitor, no VM restart).
ISO `SP-PLUS-cycle35.iso`, sha256 `7adc341c2660bc09ad0af7a1dcb17fbb831bf05b17d4cf0a67c7e4cfd90314ea`.

**Caveat on this sweep:** the machine was in active use by Christopher while it ran.
`~/.config/kdeglobals` was rewritten at 18:59:31, mid-sweep, which changed one result
between passes. Findings below are from the second pass unless stated.

## Verdict

**Not shippable as-is.** Two defects, one of them security-relevant. Neither was caught
by the build gates.

---

## DEFECT 1 (BLOCKER) — the Calm look-and-feel is named but its contents are not applied

`LookAndFeelPackage=org.secureprospective.spplus.calm.dark` is set in the user's
`kdeglobals`. The package's own `contents/defaults` prescribes three things. None of them
are in effect:

| Prescribed by the LNF package | State on the installed system |
|---|---|
| `ColorScheme=SPPlusCalmDark` | **absent** — only a stale `ColorSchemeHash=` remains |
| `theme=__aurorae__svg__spplus-calm-dark` | **absent** — `kwinrc` has no `theme=` line at all |
| `widgetStyle=Breeze` | **absent** |

Both `.colors` files ARE installed in `/usr/share/color-schemes/`. The wallpaper DID apply
and verify. So the advisor gets the SP+ wallpaper on a desktop wearing none of the
graphite palette and none of the glow window decorations — the entire cycle35 deliverable.

This is DN-24 recurring: naming a look-and-feel is not applying it.

**What makes it unrecoverable, and is the real bug:** `spplus-first-login` writes its
completion sentinel `~/.local/state/sp-plus/first-login-theme-applied` (written 18:50:12)
and the unit carries `ConditionPathExists=!` on it. The unit is therefore **skipped
forever** — confirmed in the journal on the next boot. A first login that half-applied the
theme can never retry.

**Why the script did not notice.** Its own comments show the read-back lesson was already
learned — but applied only to the wallpaper:

```
/usr/sbin/plasma-apply-lookandfeel -a "$LNF" --resetLayout || rc=1      # exit code only
...
if grep -qF "$WALLPAPER" "$APPLETSRC"; then wp_ok=1; ...                 # config read-back
```

The look-and-feel is trusted on its exit code; only the wallpaper is verified against the
config. The unit then logged `applied org.secureprospective.spplus.calm.dark` — a claim it
never checked — and stamped the sentinel.

**Fix direction:** verify the look-and-feel the same way the wallpaper already is — read
`ColorScheme`, `kwinrc theme=` and `widgetStyle` back out of config, retry on mismatch, and
**only stamp the sentinel when every one of them reads back correctly.** A partial apply
must leave the sentinel unwritten so the next login retries.

**Not established:** why the apply did not take. `--resetLayout` reloads plasmashell
asynchronously and the script's own comments record plasmashell flushing cached config over
a prior write. That is the leading hypothesis, not a conclusion — it has not been tested.

## DEFECT 2 (SECURITY) — wsdd runs with none of its hardening flags

The unit intends:

```
Environment="OPTIONS=--discovery --no-host --listen 127.0.0.1:5357"
ExecStart=/usr/bin/wsdd --shortlog --chroot=/run/wsdd $OPTIONS
EnvironmentFile=-/etc/sysconfig/wsdd
```

The **running process** is `/usr/bin/wsdd --shortlog --chroot=/run/wsdd` — `$OPTIONS`
expanded to nothing.

Cause: the wsdd RPM ships `/etc/sysconfig/wsdd` containing `OPTIONS=""`, and systemd
applies `EnvironmentFile=` **after** `Environment=`, so the file wins and wipes all three
flags.

Observed consequence (`ss` on the guest):

```
LISTEN 10.0.2.15:5357                       <- LAN address, not 127.0.0.1
LISTEN [fe80::5054:ff:fe9f:2ba6]%enp1s0:5357
UNCONN 10.0.2.15:3702 / 239.255.255.250:3702 / 0.0.0.0:45561
```

So an advisor's machine **advertises itself over WS-Discovery and listens on the LAN**,
when SP+ specified host-advertisement off and localhost-only. On a client's network that is
exactly the opposite of intent.

**Fix direction:** do not depend on `$OPTIONS`. Ship a drop-in
`/usr/lib/systemd/system/wsdd.service.d/` that clears and restates `ExecStart` with the
flags literal, so a distro-owned `/etc/sysconfig` file cannot silently disarm it.

**Why the gates missed both:** `WSDD_OK` only asserted the package was installed.
`field-inspect` 10b does assert `--no-host` in the live process, but that check needs root
and reported `SKIPPED_NEEDS_ROOT` on the user-context run — a skip that reads as silence,
not as failure.

## Discrepancies to reconcile

- **`spplus` uid is 958; the ledger records 960.** One of the two is wrong.
- `bootc_booted_image` reports UNKNOWN in field-inspect although `bootc status` answers
  fine — the probe is wrong, not the system.
- `firmware=legacy_BIOS`, `luks_version=absent`, `tpm_device=absent`. Expected for this
  throwaway BIOS VM, but it means **cycle35 has not exercised the UEFI + LUKS + TPM path at
  all.** That path is untested, not passing.

## Performance

Boot: **11.17s** = 969ms kernel + **7.03s initrd** + 3.17s userspace.

The initrd dominates and is the only real target. `systemd-analyze blame` is topped
entirely by device units at ~7.9s — `dev-cdrom`, `dev-sr0`, the SPICE and guest-agent
virtio ports. These are QEMU artifacts, so **this figure is not representative of advisor
hardware** and should be re-measured on metal before optimising. Userspace at 3.17s is
already healthy; `tuned`/`tuned-ppd` (~575ms combined) is the longest chain link.

`/` shows `composefs 40M 100%` — this is normal for the immutable composefs root, not a
full disk. `/var` has 37G free of 48G.

## Next actions

2. Fix wsdd via a systemd drop-in (Defect 2).
3. Add a gate asserting the three LNF keys read back on the installed system, and make the
   wsdd live-process check fail rather than skip when it cannot run as root.
4. Reconcile the `spplus` uid against the ledger.
5. Plan a UEFI + LUKS + TPM install to cover the untested path.

# ADDENDUM — DEFECT 3 (BLOCKER): Node segfaults on `Intl.Segmenter`, which is what crashes Fin

Found 2026-08-27 ~19:40 while the on-screen sweep was running. Christopher's report was
*"Fin crashes just after opening it."* The cause is not in Fin.

## Reproducer — one line, 100% reliable

```
$ node-22 -e 'new Intl.Segmenter("en",{granularity:"grapheme"}).segment("hello")'
Segmentation fault (core dumped)      exit=139
```

Any `Intl.Segmenter` call segfaults the Node runtime. `"hello"` is enough.

## Evidence

Four SIGSEGVs captured on the installed system — 19:01:51, 19:02:04, 19:18:03, 19:18:45 —
all `/usr/bin/node-22`, command line `pi`. Faulting frames:

```
Signal: 11 (SEGV)
#0  v8::internal::JSSegments::Create(...)
#1  v8::internal::Builtin_SegmenterPrototypeSegment(...)
```

Screenshots `13-fin-login-before` -> `14-fin-login-result` -> `15-fin-login-after-crash`
in `sweep35-evidence/` show it dying around `/login`, which is the action the Fin banner
instructs the advisor to take. Fin's TUI calls `Intl.Segmenter` for grapheme-aware cursor
and wrapping on keystrokes, so it dies seconds after opening.

**A superseded reading, recorded so it is not repeated:** several threads appear in
`clipboard.linux-x64-gnu.node` and were briefly taken as the lead. They are parked in
`syscall` — idle workers, not the fault. The clipboard addon is not implicated.

## Root cause — proven, not inferred

`images/kde/Containerfile:316`:

```
RUN dnf install -y --setopt=install_weak_deps=False nodejs npm
```

On the installed system:

- `/usr/bin/node-22` is provided by `nodejs22-22.23.1-2.fc44`
- that package **recommends** `nodejs22-full-i18n(x86-64) = 1:22.23.1-2.fc44`
- installed are `nodejs22`, `nodejs22-bin`, `nodejs22-libs` — **`nodejs22-full-i18n` is absent**

`--setopt=install_weak_deps=False` drops the recommended ICU data package. Node falls back
to small-ICU, which omits the break-iterator data `Intl.Segmenter` requires, and V8
segfaults instead of failing gracefully. Node reports ICU 78.2 while the system carries
libicu 77.1, and `ldd` shows no dynamic ICU linkage — all consistent.

**This is a runtime defect, not a Fin defect.** Anything Node-based on SP+ that touches
`Intl.Segmenter` fails identically. Fin is simply the first thing an advisor opens.

## Fix

Add **`nodejs22-full-i18n`** to the existing dnf line. Weak deps stay disabled by policy;
the needed package is named explicitly. Exact name and version confirmed available.

## Gate to add

The reproducer is the gate. In the image build:

```
node-22 -e 'new Intl.Segmenter("en",{granularity:"grapheme"}).segment("hello")' || exit 1
```

Existing gates asserted that files and binaries *exist*; none executed the runtime. That is
the class of gap that let this ship — a gate that proves the thing runs, not that it is
present.

## Method note

This was found only because the sweep ran against the live desktop. Neither the SSH pipe
run nor the TTY run reproduced it. Christopher's instruction to make the testing happen
on-screen is what surfaced it.
