## What it contains

Exactly the four tables the locked scope names (`docs/NO_CRM_ARCHITECTURE.md`,
"Scope locked, 2026-08-15"): `contacts`, `deals`, `activities`, `event_log`.

### contacts

Name, email, phone, source, notes, plus `version` and epoch timestamps.

`email` is indexed but deliberately **not** UNIQUE. Shared inboxes and role
addresses are real, and a uniqueness constraint would reject a legitimate second
person rather than prompt a merge. Deduplication is an app-level judgment call.

### deals

Belongs to a contact. `stage` is a named string enum with a CHECK
(`new` / `qualifying` / `proposal` / `negotiation` / `won` / `lost`), following
0004's `step` reasoning: a named value survives a later insertion into the list,
an integer code silently reclassifies everything.

`next_action` (plain language) plus `next_action_at` (epoch seconds) are the
load-bearing pair. The "what has gone quiet" weekly report in the architecture
doc's first-build sketch is a date-range query over `next_action_at`, so that
column is indexed.

### activities

Type, summary, optional longer body, `occurred_at`, `created_at`. Attached to a
contact, a deal, or both; both FK columns are nullable so a contact-only note or
a deal-only note both work, though an activity attached to neither is not
reachable by any real query and the app should refuse to write one.

`external_ref` holds a Gmail `Message-ID` or Calendar event id where one exists.
That is the minimum hook needed for the sync-drift failure mode (#4) to be
*detectable* later. It is not a sync log, and I did not build one; a `sync_log`
table is a real named need but is not among the locked four.

Activities are ordinary editable business records. That distinction from
`event_log` is stated explicitly in the file so nobody treats the two as
interchangeable.

### event_log

The append-only spine, and the one thing here that cannot be retrofitted.

- Never updated, never deleted. The file says so in a prominent block comment
  above the table, in plain language, including the specific rationalizations
  ("just this once", cleaning up test data, fixing a typo, during a migration)
  so a future reader does not talk themselves into an UPDATE.
- A correction is a new row pointing at the row it corrects via
  `corrects_event_id INTEGER REFERENCES event_log(id)`, with a free-text `note`
  for why. The original is left untouched forever.
- Every row records: `actor` + `actor_type` (who), `action` (what),
  `entity_type` + `entity_id` (which), `occurred_at` (when),
  `before_json` / `after_json` (state change).
- `occurred_at` and `recorded_at` are separate columns. In a polling
  architecture with no event bus (failure mode #3), a cron run routinely
  discovers something well after it happened, and collapsing the two would
  quietly falsify the timeline.
- The comment block also states, in the file itself, that this is the one table
  that cannot be reconstructed after the fact, so the reason for the discipline
  travels with the schema rather than living only in a doc.

**Not built, per the locked deferrals:** hash-chaining, tamper-evidence,
signatures, retention automation, RBAC. The file names these as deliberately
absent so their absence reads as a decision rather than an oversight.

## Failure modes addressed

- **#1 concurrent edits / last-write-wins.** `version INTEGER NOT NULL DEFAULT 1`
  on `contacts` and `deals`. The header spells out the required update form
  (`SET ..., version = version + 1 WHERE id = ? AND version = ?`) and states that
  zero rows changed must be surfaced as a conflict, never swallowed as success.
  `activities` and `event_log` have no version column on purpose since nothing
  updates them.
- **#2 no enforced relational integrity.** Foreign keys are declared properly
  (`deals.contact_id`, `activities.contact_id`, `activities.deal_id`,
  `event_log.corrects_event_id`) with a header comment stating that D1 does not
  enforce them by default and that app-level existence checks remain required.
  0004's header already flagged the same uncertainty about `ON DELETE CASCADE`
  behaviour; I repeated the warning rather than assume it has been settled since.

## Indexes

`contacts(email)`, `contacts(created_at)`; `deals(contact_id)`, `deals(stage)`,
`deals(next_action_at)`; `activities(contact_id, occurred_at)`,
`activities(deal_id, occurred_at)`, `activities(occurred_at)`,
`activities(external_ref)`; `event_log(entity_type, entity_id, occurred_at)`,
`event_log(occurred_at)`, `event_log(actor, occurred_at)`,
`event_log(action, occurred_at)`, `event_log(corrects_event_id)`.

Chosen for the queries the architecture doc actually describes: contact lookup by
email, pipeline by stage, the no-touch report by next-action date, an entity's
audit trail, and any date-ranged reporting.

## Style notes

Matched against 0002 and 0004. Timestamps are **INTEGER epoch seconds**, the 0004
and 0005 convention, not 0002's `TEXT DEFAULT (datetime('now'))`, which is the
older style. Text UUID primary keys for rows referenced by id; `event_log` uses
`INTEGER PRIMARY KEY AUTOINCREMENT` matching `kit_audit_log`. `CREATE TABLE IF NOT
EXISTS` and `CREATE INDEX IF NOT EXISTS` throughout. JSON in `_json`-suffixed TEXT
columns. Zero em dashes, verified by grep at 0.

## OPEN QUESTION for Christopher: which database does this bind to?

Not my call and I did not make it. This project keeps one isolated D1 per app,
and 0004's header records what happened the last time that rule was assumed away.
The candidates as I see them:

1. **A new database**, for example `secureprospective-workspace-db`, bound as
   something like `WORKSPACE_DB`. Most consistent with the one-per-app rule. This
   would be the fourth D1 in the Pages project alongside `BACKOFFICE_DB`,
   `ECOSYSTEM_DB`, and `KIT_DB`.
2. **Reuse `ECOSYSTEM_DB`**, which already exists and is bound but whose current
   contents `CLAUDE.md` says should be verified rather than assumed empty.

Option 1 looks right to me on the stated rule, but the decision is yours and the
migration is deliberately written to be database-agnostic. Nothing in the file
names a binding.

## Things I was unsure about

- **Whether `deals` should carry an amount or value column.** I left it out.
  "Opportunities linked to a contact, stage, next action, next action date" was
  the brief and the locked scope says commission and money engineering comes
  later. Easy to add, and a genuinely retrofittable column.
- **`activities.type` enum values.** I picked `email`, `call`, `meeting`, `note`,
  `task` as the obvious v1 set. A CHECK constraint means adding a value later
  requires a table rebuild in SQLite, which is the tradeoff for the constraint
  actually holding. If that list feels too tight, say so now while it is cheap.
- **`event_log.actor_type` values** are `human`, `system`, `claude`. Splitting
  `claude` out from `system` seemed worth it given failure mode #7 (non-determinism
  at the write path): being able to filter the log to only AI-originated writes is
  most of the value of having the log at all when a bad write needs finding.
- **No `sync_log` table.** Named as a real need in the failure modes but not among
  the locked four, so I did not add it. Flagging rather than deciding.
- **`ON DELETE CASCADE` on `deals.contact_id` and the activity FKs.** Correct
  intent, but per 0004's own unresolved note it should be confirmed with an actual
  delete against real D1 before anyone relies on it for data-removal purposes.
  Deleting a contact should probably be a soft operation anyway once there is an
  event log, but that is app design, not schema, and not this chunk.
